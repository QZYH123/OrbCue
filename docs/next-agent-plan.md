# 下一 Agent 会话实现计划（已废弃）

> 本文件是早期版本，未按 `$ask-matt` 的 issue/ticket 流程编写。请以 [`docs/agent-handoff.md`](./agent-handoff.md)、父 issue 和 `.scratch/agent-activity-dock/issues/` 下的 tickets 为唯一执行依据。

## 目标

实现一个可验证的 Agent Activity Dock 最小原型，先回答一个问题：用户把 Agent 放到后台后，是否能用一个几乎不占空间的小球，可靠知道“还有多少任务在跑”和“该回来看看了”。

本次计划只覆盖核心体验和性能，不实现完整的跨 Agent 产品。

## 已确认的行为

### 小球

- 小球是独立的、固定尺寸的置顶小窗口，不强行改变原终端窗口的形状。
- 多个任务共用一个小球，避免每个 Agent 打开一个窗口。
- 小球显示 `工作数量/追踪数量`，例如 `2/3`。
- 小球边框颜色表示整体状态：至少一个任务工作中时使用工作色，全部停止时使用空闲色。
- 小球主状态只有“工作中”和“不在工作”两种；不要为完成、报错、等待输入各做一套主视觉。
- 有新情况但用户尚未查看时，在角落保留一个小 `!`。它是待查看标记，不是第三种工作状态。
- 点击小球或使用热键进入任务列表/详情；普通工作事件不能强制展开或移动小球。

### 状态来源

- Agent、Skill 或 MCP 在开始时发送工作事件，在正常结束、报错或等待用户输入时发送停止事件。
- Dock 只消费明确的状态事件，不扫描进程、终端内容、transcript、命令或屏幕。
- MVP 不做心跳、不做周期轮询、不做自动崩溃检测。
- 强制终止、断电或事件丢失时，状态可能暂时停在“工作中”；提供手动重置操作作为兜底。
- 同一任务重复发送停止事件不能重复播放提示或重复增加任务数量。

### 提示

- 从工作中切换到停止时播放一次短提示音，并做一次短暂视觉闪动。
- 提示不能重复轰炸；`!` 持续到用户查看对应任务或执行明确的清除操作。
- 音频失败不能阻止状态更新，也不能影响 Agent。

### 性能

- 无事件时不轮询、不持续重绘、不运行动画循环，CPU 使用应接近零。
- 事件到达后 100ms 内完成内存状态和小球视觉更新。
- 常驻动画不是目标；只允许一次性的短闪动。

## MVP 范围

### 必须完成

1. 纯内存的任务注册表和确定性的状态聚合。
2. 一个本地 CLI 事件发送器，例如 `dock start`, `dock stop`, `dock attention`, `dock reset`，具体命令名由实现者决定但必须有清晰帮助文本。
3. 一个只允许当前用户访问的本地 IPC 通道。
4. 一个轻量悬浮窗口 presenter：固定尺寸、置顶、边框颜色、任务计数、`!` 标记、点击/热键入口。
5. 可注入的提示音接口和一次性提示策略。
6. 一个通用 Skill/MCP 调用示例，证明外部 Agent 不需要导入 Dock 内部模块就能发送事件。
7. 单元测试、IPC 集成测试和基本的人工视觉验收。

### 明确不做

- 心跳、租约、超时推断和进程扫描。
- 把原终端窗口跨终端地改造成小球。
- Codex、Claude、DSH 的完整一方 adapter；先用通用 CLI/示例验证协议。
- Agent 控制、权限批准、文本输入、命令执行或 transcript 读取。
- 云端、网络监听、多用户、遥测、账号和远程控制。
- 历史数据库、跨重启恢复、复杂审计页面和完整通知设置面板。
- 每个 Agent 一个独立悬浮球。

## 建议的最小结构

实现者可按仓库最终语言调整文件名，但保持这些职责分离：

- `event_contract`：定义最小事件字段和边界。
- `event_ingress`：解析、大小限制、当前用户 IPC、错误响应。
- `task_registry`：按任务 ID 保存当前是否工作、是否待查看、来源和终端定位信息。
- `state_aggregator`：计算工作数量、追踪数量、整体边框状态和待查看数量。
- `attention_policy`：决定何时短音、短闪、设置或清除 `!`。
- `presenter`：只接收只读快照，不直接修改任务状态。
- `cli_emitter`：给 Skill/MCP 和人工测试使用的薄封装。
- `sound_sink`：异步、可替换；测试使用 fake sink，生产实现使用平台声音适配器。

状态层不要依赖任何具体 Agent。Agent 名称只是来源字段，任务 ID 才是一次可独立追踪的任务。

## 交接顺序

### 阶段 0：先做运行时和窗口能力探针

1. 阅读 `CONTEXT.md`、`docs/adr/0001-0003*.md` 和本计划。
2. 确认当前环境能否创建 32–48px、无装饰、置顶、可点击的窗口，并测量窗口创建到显示的延迟。
3. 当前环境已知是 WSL2，有 X/Wayland 变量；Python 3.12 和 Node 24 可用，但 Tkinter、GTK introspection 和固定终端类型不可直接假设。
4. 优先选择能用现有运行时完成的轻量 GUI 路线；不要默认引入 Electron。若必须安装依赖，先记录依赖、体积和启动成本，再决定。
5. 若无法可靠聚焦原终端，先实现小球点击打开任务列表；把“聚焦源终端”隔离成后续 presenter 能力，不阻塞状态核心。

### 阶段 1：先写状态核心和测试

1. 先定义最小事件：任务 ID、来源、事件 ID、时间、动作/结果、可选终端定位信息。
2. 实现开始、正常结束、报错、等待输入、手动重置五条路径。
3. 规定重复事件的行为：重复开始不增加任务；重复停止不重复提示；重置只清除指定任务或明确指定的全部任务。
4. 让聚合快照至少包含：工作数量、追踪数量、整体工作标志、待查看数量、任务列表。
5. 用 fake clock 和 fake sound sink 覆盖状态转换、重复投递、多任务计数和提示去重。

### 阶段 2：接入本地事件通道

1. 使用当前用户专用的本地 IPC；优先 Unix domain socket 或同等本机机制，不开网络端口。
2. CLI 发事件后快速收到 accepted/rejected 结果，不等待声音或窗口绘制。
3. 对空载荷、错误任务 ID、超长消息、非法事件动作做拒绝测试；被拒绝事件不能改变现有状态。
4. 增加一个最小 Skill/MCP 示例，只负责调用 CLI 或 IPC，不把 Dock 状态模块嵌入 Agent。

### 阶段 3：实现聚合小球 presenter

1. presenter 只消费状态快照，不能通过读取终端或进程补全状态。
2. 固定窗口大小，避免数字变化导致窗口抖动；至少能稳定显示 `0/0`、`1/1`、`2/10` 等长度。
3. 工作数量大于零时显示工作边框色，否则显示空闲边框色；计数文字同时提供非颜色的状态线索。
4. 有待查看任务时显示小 `!`；查看后通过显式回调清除，不因普通工作事件自动清除。
5. 点击先打开紧凑任务列表；若当前环境有可靠的窗口聚焦能力，再增加“回到源终端”动作。
6. 热键必须有清晰的注册失败诊断；热键不可用时点击仍可完成主要流程。

### 阶段 4：接入提示和人工验证

1. 用异步 sound sink 播放一次短提示；声音失败时记录一次诊断并继续提交视觉状态。
2. 手动验证：启动 1 个任务、启动多个任务、结束其中一个、全部结束、报错、等待输入、重复停止、手动重置。
3. 验证小球不会因为普通开始/工作事件自动展开、移动或持续闪烁。
4. 验证错过声音时 `!` 仍然可见，查看任务后才消失。

## 测试与验收

### 自动化测试

- 状态转换：开始、结束、报错、等待输入、重置。
- 聚合计数：多任务并行、重复开始、重复停止、清除一个任务、清除全部任务。
- 提示策略：每个停止任务只提示一次；重复事件不重复提示；声音 sink 抛错不回滚状态。
- 事件入口：非法 JSON、未知动作、超长消息和错误用户权限不会污染注册表。
- presenter 合同：快照能提供边框状态、`working/tracked`、待查看标记和任务列表；测试不要绑定具体 GUI 工具包内部对象。
- IPC 集成：真实 CLI 到 daemon 到状态快照的链路可用。

### 性能验收

- 空闲 30 秒期间没有周期性 IPC、进程扫描或重绘计时器。
- 事件发送到状态快照更新小于 100ms；窗口更新延迟单独记录，不把音频播放算入事件响应。
- 普通工作事件不触发声音和常驻动画。
- 多任务计数不会随重复事件无限增长。

### 人工验收

- 小球能稳定置顶且不遮挡主要工作区域；窗口尺寸固定。
- 用户在其他窗口工作时，能一眼看出 `工作数量/追踪数量` 和边框状态。
- 结束、报错、等待输入都能让用户意识到“该回来看看了”；错过声音也能通过 `!` 发现。
- 强制结束 Agent 后，手动重置可以恢复小球；系统不需要扫描 Agent 才能运行。

## 下一会话的交付顺序

下一 Agent 会话结束时应交付：

1. 可运行的最小 daemon、CLI 和 presenter，或明确记录 GUI 依赖阻塞点。
2. 状态核心和 IPC 的自动化测试。
3. 一份运行说明，包含启动 daemon、发送开始/结束/等待/报错/重置事件的命令。
4. 一份实测结果：事件延迟、空闲 CPU 行为、窗口是否置顶、声音失败时的降级行为。
5. 只在核心体验通过后，再决定是否进入 Codex/Claude/DSH adapter 和持久化。
